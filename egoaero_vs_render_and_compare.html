HOI reconstruction, side by side

render_and_compare  a CHOIR reproduction  ·  egoaero  an EgoAERO reproduction  — compared at the reconstruction-stage level.

Both folders live under hoi_recon/ and both reconstruct 4D hand–object interaction (per-frame MANO hand + object geometry + 6-DoF object trajectory + contact) through a 9-stage, file-based, mock-runnable pipeline. But they reproduce different papers, take different inputs, order their stages differently, and take opposite stances on how "real" the mock path is. This page maps them stage-by-stage and then digs into every meaningful difference.

render_and_compare = CHOIR (Contact-aware 4D HOI Recon, render-and-compare spine)
egoaero = EgoAERO (asset-free egocentric recon, Sec 2.1 / App A–E)

1. TL;DR — the five real differences

render_and_compare

  • Input: monocular RGB video (depth is estimated, MoGe/DA3).
  • Viewpoint: third-person primary (egocentric optional behind one hand interface).
  • Mock = error sandbox: inject realistic per-stage perception error onto GT, then real geometric refinement drives it back down; stage 8 measures the drop.
  • Real backends are wired (lazy import, two conda envs, subprocess) and degrade gracefully — swap in weights and it runs.
  • Ends at reconstruction: exports pseudo-GT for distilling a future feed-forward model. It is an error-characterization rig.

egoaero

  • Input: egocentric RGB-D (depth is a given channel).
  • Viewpoint: egocentric-only (head-mounted, moving camera = ego motion).
  • Mock = GT-driven: stages pass GT through with injected noise; only the contact optimization and quality scoring run real algorithms.
  • Real backends are hard-stubbed — every real path raise NotImplementedError via backends/real.py; only mock runs today.
  • Reconstruction is step 1 of 4: feeds a two-stage RL policy, an online quality gate, and a dataset-collection loop (SP2–SP4).

Read this: the biggest structural difference is order & placement. render_and_compare reconstructs hand first (S2), object second (S3) then aligns and rectifies before a single big differentiable contact optimizer (S7). egoaero reconstructs object first (S2 track, S3 mesh), hand later (S4), compensates ego motion into a table frame (S5), then does a bounded geometric contact repair (S6) and a quality gate (S8). The contact step is S7 in one and S6 in the other; the eval step is S8 vs S7.

5. Real-vs-mock philosophy — the deepest difference

render_and_compare — error sandbox, backends wired

Mock generates a synthetic GT scene, then injects realistic perception error in the perception stages (stage 2 depth-dominant hand jitter, stage 3 object scale/depth/6-DoF drift). The geometric refinement stages run for real on that noisy data and drive the error back down; stage 8 re-derives GT and prints the before→after drop.

Every real backend is actually wired via backends/real_perception.py with lazy imports and a graceful BackendNotAvailable — install weights and --real runs the real model. Heavy models live in a second sam3d-objects conda env, called by subprocess with per-run caching.

gate pattern: if cfg.mock: …inject… else: from ..backends.real_perception import …

egoaero — GT-driven, backends stubbed

Mock generates a synthetic GT scene; the perception stages mostly pass GT through (with smaller injected perturbations: stage-2 translation drift, stage-4 depth bias). Only two stages run a real algorithm: the App-C contact optimization (stage 6) and the App-E quality scoring (stage 8) — both pure numpy, no learned model.

Every real backend is a hard stub: stages 0–5 begin with if not cfg.mock: raise NotImplementedError(...), and backends/real.py:get() unconditionally raises naming the would-be models. There is no --real path that runs today.

gate pattern: if not cfg.mock: raise NotImplementedError("real … — backends/real.py")

12. Downstream scope — where they diverge entirely

render_and_compare ends at reconstruction

Stage 8 exports pseudo_gt.npz + distillation signals + (real mode) reprojection-overlay validation videos. The stated goal is to be a teacher whose cleaned 4D-HOI becomes training data for a future single feed-forward model. It also ships HTML reports (pipeline_report.html, method_comparison.html) and a viser viewer for error inspection.

egoaero reconstruction feeds a closed loop

Reconstruction (SP1) is one of four sub-projects: SP2 retargets the hand-object trajectory to a simulated Shadow Hand and trains a two-stage residual RL policy (MuJoCo + PPO); SP3 is the online quality gate (stage 8); SP4 runs a collection loop (reconstruct → assess → accept/repairable/recapture) that writes an EgoDex-R-style dataset. Reconstruction is the front end of an asset-free demo→sim→robot system.

13. Shared DNA

Despite the differences, the two are clearly siblings:
  • 9-stage, file-based pipelines — each stage writes a numpy Bundle (arrays.npz + meta.json); resumable; selectable stage ranges; cached unless forced.
  • Mock-runnable on a CPU box with no weights — both ship a deterministic synthetic UV-sphere + procedural-hand reach→grasp scene (same R=0.040 m sphere, same 778-vert hand, raised-cosine grasp bump).
  • MANO hand · asset-free object · contact-aware refinement · before/after eval.
  • Swappable real backends behind a registry (one wires them, one stubs them).
  • An interactive viser 4D viewer + a comparable per-clip contract (hand verts/joints, object mesh, 6-DoF poses, contact).
In short: render_and_compare is a third-person, RGB-in, render-and-compare CHOIR error-characterization rig that ends at pseudo-GT; egoaero is an egocentric, RGB-D-in, asset-free EgoAERO reproduction whose reconstruction front-ends an RL + data-collection loop. They agree on the destination (clean 4D HOI) and diverge on the road.
